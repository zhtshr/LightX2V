## 测量范围

Wan2.2 A14B MoE INT8，480×832、81 帧、4 steps，SP=1/2/4/8。输出校验全部通过。先完成正常计时，再单独采集预热后的单请求 rank0 CPU/CUDA trace，其他 rank 正常参与通信。原吞吐表未改动。

## 8 卡扩展损失的来源

单卡 GPU 跨度 14.7836 s，理想 8 卡 1.8479 s，实际 2.1131 s，差额约 **265.2 ms**。计算项按“8 卡时间 − 单卡时间/8”估计额外开销。

| 来源 | 额外时间 | 占差额 |
|---|---:|---:|
| NCCL（包含 kernel 内等待） | 98.4 ms | 37.1% |
| 拷贝、拼接等数据搬运 | 76.9 ms | 29.0% |
| GPU 空闲间隙 | 28.6 ms | 10.8% |
| 逐元素及其他操作 | 16.9 ms | 6.4% |
| INT8 GEMM | 16.4 ms | 6.2% |
| 注意力 | 13.3 ms | 5.0% |
| 归一化/归约 | 9.6 ms | 3.6% |
| 量化 | 5.2 ms | 2.0% |

分类内使用 GPU 时间区间并集；拷贝等细分类按 kernel 名称统计时长和。少量跨 stream 重叠及四舍五入使各项不保证严格相加。

## 结论

- 纯 NCCL 约占损失的 37%，并非多数；NCCL 加额外数据搬运合计约 66%，是主要来源。不能把所有扩展损失等同于 NVLink 传输慢。
- 注意力从 10.03 s 降至 1.27 s，INT8 GEMM 从 2.87 s 降至 0.38 s，主计算接近线性扩展，没有明显效率塌陷。
- GPU 空闲间隙在 8 卡约 32 ms，确实存在固定调度/同步等开销，但不是主要来源。仅凭间隙不能区分 Python、launch、依赖等待。
- NCCL 时长包含等待其他 rank，不能单独推断带宽利用率。拷贝分类包含数据重排和其他复制，尚不能全部归为 All-to-All 打包；上述为 trace 归因而非消融结果。
- 优先检查 Ulysses 的 contiguous/copy/cat，减少临时复制、融合数据重排，再优化通信与同步。仅隐藏 NCCL 无法消除数据搬运和固定开销。
- 本次为单请求轨迹，不能直接解释双请求 overlap 无收益的全部原因；现有 overlap 的保守同步与资源竞争需另行分析。
